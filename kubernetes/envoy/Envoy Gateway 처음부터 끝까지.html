1

Envoy와 Envoy Gateway

이름이 비슷하지만 하나는 일꾼이고, 하나는 관리자입니다.

Envoy

요청을 받아서 알맞은 곳으로 넘겨주는 프록시 프로그램입니다. nginx 같은 리버스 프록시라고 보면 됩니다. 실제로 트래픽이 지나가는 곳입니다.

Envoy Gateway

Envoy를 관리하는 컨트롤러입니다. Gateway와 HTTPRoute를 읽어서 Envoy를 띄우고 규칙을 넣어줍니다. 요청은 이곳을 지나가지 않습니다.

nginx는 설정 파일을 고치고 reload해야 하지만, Envoy는 실행 중에 API로 설정을 실시간으로 받습니다(xDS 방식). 그래서 HTTPRoute를 apply하면 Envoy Gateway가 그 내용을 바로 Envoy에 밀어주고, Envoy는 재시작 없이 새 규칙을 적용합니다.

Envoy는 문지기이고, Envoy Gateway는 문지기에게 근무 지침을 내려주는 관리자입니다.

2

구성 요소

사람이 만드는 것과 컨트롤러가 자동으로 만드는 것으로 나뉩니다.

구성 요소정체누가 만드나
envoy-gateway (Deploy, Pod, Svc)컨트롤러 프로그램. 관리자helm 설치 시 생성
GatewayClass“이 클래스는 어느 컨트롤러가 담당한다”는 등록서사람
Gateway“입구를 하나 만들어 달라”는 요청서사람
HTTPRoute어느 Gateway에서, 어떤 Host와 path를 어디로 보낼지 정한 규칙사람
EnvoyProxyEnvoy를 어떻게 띄울지 정하는 설정 (Svc 타입, LB IP, Pod 수 등)사람 (선택)
envoy-{ns}-{gateway명}-{해시} (Deploy, Pod, Svc)실제 Envoy 프록시와 그 LoadBalancer컨트롤러가 Gateway마다 자동 생성

GatewayClass는 컨트롤러가 아닙니다

GatewayClass의 CONTROLLER 열에 보이는 gateway.envoyproxy.io/gatewayclass-controller는 Pod 이름이 아니라 담당자 이름표(문자열)입니다. envoy-gateway Pod가 “나는 이 이름표 담당”이라고 하면서 클러스터의 GatewayClass를 훑어보고, 이름표가 맞으면 받아들입니다. 그 결과가 ACCEPTED: True입니다.

비유실제
관리 회사envoy-gateway Pod
“이 건물은 OO 관리회사가 담당”이라는 계약서GatewayClass
“입구 하나 만들어 주세요” 요청서Gateway
관리회사가 배치한 경비원Envoy Pod

왜 Envoy는 전부 envoy-gateway-system에 생기나

helm으로 설치할 때 -n envoy-gateway-system으로 지정했기 때문에 컨트롤러가 그 namespace에 있고, 기본 동작상 컨트롤러는 Envoy를 자기 namespace에 모아서 만듭니다. Gateway가 cobim namespace에 있어도 마찬가지입니다. 컨트롤러 권한을 좁게 유지하고, 인프라를 한곳에서 관리하기 위한 설계입니다.

# 설치 방식 확인
helm list -A | grep -i gateway

lakehouse-gateway가 envoy-gateway-system에 있는 건 helm과 관계없습니다. 누군가 Gateway를 만들 때 그 namespace를 고른 것입니다.

최근 버전(v1.5 이후로 알려짐)은 Envoy를 Gateway와 같은 namespace에 만드는 GatewayNamespace 모드도 지원합니다. 컨트롤러 전체 설정이라 바꿀 때는 영향 범위를 먼저 확인하세요.

3

Gateway를 만들면 생기는 일

yaml 하나를 apply하면 컨트롤러가 나머지를 처리합니다.

  1. kubectl apply -f gateway.yaml
  2. 컨트롤러가 감지합니다. gatewayClassName: eg를 보고 자기 담당인지 확인하고, 연결된 EnvoyProxy가 있으면 그 설정을 읽습니다.
  3. Envoy Deployment를 만들고 Pod를 띄웁니다. Pod가 2/2인 이유는 envoy 컨테이너와 shutdown-manager 컨테이너가 함께 있기 때문입니다.
  4. Envoy Service를 만듭니다. 기본 타입은 LoadBalancer이고, 포트는 Gateway의 listener를 그대로 따릅니다.
  5. 클라우드(NHN Cloud)가 LB를 만들고 EXTERNAL-IP를 발급합니다.
  6. 컨트롤러가 Gateway status에 ADDRESS와 PROGRAMMED: True를 기록합니다.
  7. 이후 HTTPRoute가 parentRefs로 이 Gateway를 지정하면, 컨트롤러가 라우팅 규칙을 이 Envoy에만 넣습니다.
# 상태가 이상할 때
kubectl describe gateway -n cobim cobim-gateway
kubectl describe svc -n envoy-gateway-system envoy-cobim-cobim-gateway-65fd4c21
kubectl logs -n envoy-gateway-system deploy/envoy-gateway --tail=100

EXTERNAL-IP가 <pending>에서 멈춰 있으면 5단계, 즉 클라우드 LB 생성 쪽 문제입니다. Svc의 이벤트를 보세요.

4

우리 클러스터 지금 모습

Gateway가 두 개이고, Envoy도 완전히 별개로 두 개입니다.

GatewayEnvoy (Deploy, Pod, Svc)EXTERNAL-IP포트

EnvoyProxy 연결 상태

GatewayClass eg의 parametersRef에 envoy-gateway-system/lakehouse-envoy-config가 걸려 있습니다. 클래스 전체에 거는 방식이라 cobim-gateway도 같은 설정으로 떠 있습니다. ClientTrafficPolicy, BackendTrafficPolicy, SecurityPolicy는 없습니다.

cobim-api-routes는 어디에 붙어 있나

parentRefs가 lakehouse-gateway입니다. 그래서 cobim.internal 규칙은 125.6.39.53의 Envoy에만 있습니다. HTTPRoute(cobim)와 Gateway(envoy-gateway-system)의 namespace가 다른데도 Accepted: True이니, Gateway의 listener가 다른 namespace의 라우트를 허용하고 있다는 뜻입니다.

5

포트와 IP는 어디서 정하나

자동 생성된 Svc를 직접 고치면 컨트롤러가 되돌립니다. 항상 Gateway나 EnvoyProxy를 고칩니다.

Svc의 80:30927이 뜻하는 것

내 PC
  ↓  133.186.152.59:80       ← port. 사용자가 접속하는 포트 (listener로 지정)
NHN Cloud LB
  ↓  워커노드:30927          ← nodePort. LB와 노드 사이 연결용 (자동 할당)
워커노드
  ↓  Envoy Pod:10080         ← targetPort. Envoy 컨테이너 (1024 미만은 +10000)
Envoy

사용자는 80과 443만 알면 됩니다. 30927은 LoadBalancer 타입 Svc가 내부적으로 함께 만드는 NodePort입니다.

바꾸고 싶은 것고치는 곳
포트 (80, 443 등)Gateway yaml의 listeners
EXTERNAL-IP, Svc 타입, 어노테이션, NodePort 고정EnvoyProxy yaml
Envoy Pod 개수, CPU와 메모리EnvoyProxy yaml

포트는 Gateway의 listener로

spec:
  gatewayClassName: eg
  listeners:
  - name: http
    protocol: HTTP
    port: 80          # → Svc port 80
  - name: https
    protocol: HTTPS
    port: 443

IP는 EnvoyProxy로 정하고 Gateway에 연결

apiVersion: gateway.envoyproxy.io/v1alpha1
kind: EnvoyProxy
metadata:
  name: cobim-envoy-config
  namespace: cobim
spec:
  provider:
    type: Kubernetes
    kubernetes:
      envoyService:
        type: LoadBalancer
        loadBalancerIP: 133.186.xxx.xxx   # 미리 확보한 Floating IP

방법 A: Gateway 하나에만

Gateway의 spec.infrastructure.parametersRef로 연결합니다. EnvoyProxy는 Gateway와 같은 namespace에 둡니다. 클래스 설정보다 우선합니다.

방법 B: 클래스 전체에

GatewayClass의 spec.parametersRef로 연결합니다. 지금 클러스터가 이 방식입니다.

NHN Cloud에서 loadBalancerIP로 IP를 고정하는 정확한 방법과 필요한 어노테이션은 NKS 문서로 확인하세요. Gateway의 spec.addresses는 Svc의 externalIPs로 들어가는 것이라 클라우드 LB IP 고정과는 다릅니다.

yaml 파일이 없을 때

클러스터에서 꺼내 볼 수 있습니다. describe는 읽기용 요약이고, 재사용하려면 -o yaml을 씁니다.

kubectl get gateway -n cobim cobim-gateway -o yaml > cobim-gateway.yaml
# 저장 후 지울 것: creationTimestamp, generation, resourceVersion, uid,
# managedFields, last-applied-configuration 어노테이션, status 전체
6

Envoy가 라우트를 고르는 법

Envoy는 Host 헤더와 path, 두 가지를 봅니다.

125.6.39.53 의 Envoy
  Host: cobim.internal           → cobim-api-routes
  Host: account.cobim.internal   → bim-service-account
  Host: 그 외                     → 매칭 없음 → 빈 404

parentRefs: 어느 Gateway에 붙을지

HTTPRoute를 추가할 때 parentRefs로 Gateway를 지정합니다. 규칙은 그 Gateway의 Envoy에만 들어갑니다. 다른 Gateway로 옮기려면 parentRefs만 바꾸면 되고, 두 개를 적으면 양쪽에서 모두 동작합니다.

hostnames: 선택 사항

hostnames를 빼면 Host가 무엇이든 path만 보고 처리하므로 IP로 바로 접속해도 동작합니다. 한 Gateway에 여러 서비스나 도메인을 올릴 때는 path 충돌을 막기 위해 넣는 게 정석입니다. Gateway listener에도 hostname을 걸 수 있고, 둘 다 있으면 겹치는 부분만 허용됩니다. *.cobim.internal 같은 와일드카드도 됩니다.

path 규칙은 위에서부터가 아니라 가장 구체적인 것부터

/api/account  → svc-bim-service-account:8082
/api/message  → svc-bim-service-message:8080   ← 현재 에러
/api/schedule → svc-bim-service-schedule:8088
/             → svc-bim-service-project:8088   ← 나머지 전부

예를 들어 /api/systemcode/list는 앞의 세 개에 해당하지 않아 마지막 /로 project 서비스에 갑니다.

7

이름을 IP로 바꾸는 방법

hosts는 Envoy가 아니라 내 PC를 위한 설정입니다.

hosts 설정이 하는 일

hosts: 125.6.39.53  cobim.internal

curl http://cobim.internal/api/systemcode/list

① 접속할 IP 찾기     cobim.internal → 125.6.39.53  ← TCP 연결에만 사용
② HTTP 요청 보내기   Host: cobim.internal          ← URL의 이름 그대로

IP는 어디로 접속할지 정할 때만 쓰이고, Host 헤더에는 원래 이름이 들어갑니다. 그래서 hosts 한 줄이 “올바른 IP”와 “올바른 Host”를 한 번에 맞춰줍니다. 브라우저도 똑같이 동작합니다.

hosts 없이 같은 효과를 내는 방법

curl -H "Host: cobim.internal" http://125.6.39.53/api/systemcode/list
curl --resolve cobim.internal:80:125.6.39.53 http://cobim.internal/api/systemcode/list

도메인 종류별 정리

도메인이름을 IP로 바꿔주는 곳hosts 필요
cobim.internal없음 (내부용 이름)필요
cobim.io실제 DNS (지금은 기존 서버)새 서버로 테스트할 때만
cobim.125.6.39.53.nip.ionip.io 공개 DNS불필요

nip.io

도메인 이름 안에 적힌 IP를 그대로 돌려주는 공개 DNS입니다. cobim.125.6.39.53.nip.io를 조회하면 125.6.39.53이 나옵니다. hosts 없이 바로 테스트할 수 있지만, 외부 DNS가 막힌 망에서는 안 될 수 있고 HTTPS는 사실상 쓸 수 없는 테스트 전용입니다.

8

테스트로 확인하기

hosts 없이 IP와 Host 헤더를 바꿔가며 보낸 네 가지 요청입니다.

빈 404 curl http://133.186.152.59/api/systemcode/list Host가 IP 그대로라 맞는 라우트가 없습니다.
빈 404 curl http://125.6.39.53/api/systemcode/list 올바른 Gateway로 갔어도 Host가 안 맞으면 라우팅되지 않습니다.
빈 404 curl -H "Host: cobim.internal" http://133.186.152.59/... Host는 맞지만 엉뚱한 Gateway입니다. cobim-gateway의 Envoy는 cobim.internal 규칙을 모릅니다.
200 curl -H "Host: cobim.internal" http://125.6.39.53/... IP와 Host가 둘 다 맞습니다. / 규칙을 타고 project 서비스가 JSON을 돌려줬습니다.

성공 조건은 두 가지입니다. 올바른 Gateway의 IP로 접속하고, 올바른 Host 헤더를 보내는 것. hosts에 125.6.39.53 cobim.internal을 넣으면 둘 다 맞춰집니다.

9

안 될 때 보는 곳

“아무 출력 없이 끝났다”는 성공이 아닙니다.

curl의 함정

curl은 응답을 받기만 하면 404나 500이어도 에러로 보지 않고, 상태 코드는 -v 없이는 보여주지 않습니다. Envoy가 보내는 404는 본문이 비어 있어서 화면에 아무것도 안 나옵니다. 처음에 133으로 “된다”고 보였던 이유가 이것입니다.

curl -v http://cobim.internal/api/systemcode/list       # 접속 IP와 상태 코드 확인
curl -f http://cobim.internal/api/systemcode/list       # 4xx, 5xx를 에러로 표시
curl -s -o NUL -w "%{http_code}\n" http://cobim.internal/...   # 코드만 (Windows)
증상의미
Could not connect, timeoutIP나 포트로 접속 자체가 안 됨
본문 없는 404Envoy까지는 갔지만 맞는 라우트가 없음
본문 있는 404, 500라우팅은 됐고 백엔드 앱이 보낸 에러
200과 데이터정상

요청이 지나가는 순서대로 로그 보기

envoy-gateway Pod는 컨트롤러라서 요청 로그가 없습니다. 가장 먼저 Envoy 프록시 Pod의 access log를 봅니다. 컨테이너가 두 개라 -c envoy가 필요합니다.

kubectl logs -n envoy-gateway-system -f \
  deploy/envoy-envoy-gateway-system-lakehouse-gateway-e4b9af21 -c envoy
응답 플래그의미볼 곳
로그 없음요청이 Envoy까지 오지 않음hosts, DNS, LB, 네트워크
NRNo Route. 맞는 라우트 없음HTTPRoute의 hostname, parentRefs, path
UH백엔드 Pod 없음Service의 endpoints
UF백엔드 연결 실패Service 포트, Pod 상태
UT백엔드 응답 타임아웃앱 로그
-정상 처리결과가 이상하면 앱 로그

그 앞단인 NHN Cloud LB는 콘솔의 Load Balancer 메뉴에서, 노드는 tcpdump -i any port 30927 -nn으로 확인할 수 있지만, 대부분은 Envoy 로그에서 갈립니다.

10

운영 도메인 옮기기 전 테스트

cobim.io는 기존 서버에서 유료 인증서로 운영 중입니다.

hosts 없음:  cobim.io → DNS   → 기존 서버       (모든 사용자)
hosts 있음:  cobim.io → hosts → 133.186.152.59  (내 PC만)

hosts는 DNS보다 먼저 확인되므로, 내 PC만 새 Envoy로 보내서 확인할 수 있습니다. 문제가 없으면 그때 DNS를 바꿉니다.

nslookup cobim.io      # DNS가 지금 어디를 가리키는지
kubectl get httproute -n cobim cobim-user -o jsonpath='{.spec.parentRefs[*].name}'

HTTPS는 인증서를 옮겨야 합니다

인증서는 서버가 아니라 도메인 기준으로 발급되므로 같은 파일을 새 서버에서 써도 됩니다. 기존 서버의 crt(체인 포함)와 key를 Secret으로 만들고 443 listener에 연결합니다.

kubectl create secret tls cobim-io-tls -n cobim --cert=cobim.io.crt --key=cobim.io.key

listeners:
- name: https
  protocol: HTTPS
  port: 443
  tls:
    mode: Terminate
    certificateRefs:
    - name: cobim-io-tls

hosts를 바꾼 뒤에는 ipconfig /flushdns를 하고 브라우저를 재시작하거나 시크릿 창을 쓰세요. 크롬은 chrome://net-internals/#dns에서 캐시를 지울 수 있습니다.

기존 사이트가 HSTS를 쓰면 브라우저가 http를 https로 강제합니다. 인증서를 옮기기 전에는 curl의 http로 먼저 확인하세요.

테스트가 끝나면 hosts에서 꼭 지우세요. 남겨두면 내 PC만 엉뚱한 곳으로 갑니다.

지금 확인된 문제 하나와, 위에서부터 내려오며 점검하는 순서입니다.

cobim-api-routes의 /api/message 규칙이 실패 중입니다. svc-bim-service-message에 8080 포트가 없습니다. 실제 포트를 확인해 HTTPRoute를 맞추세요.

kubectl get svc -n cobim svc-bim-service-message -o jsonpath='{.spec.ports}'

hosts 설정 정답

125.6.39.53   cobim.internal     # lakehouse-gateway에 붙은 라우트

점검 순서

# 1. 컨트롤러가 살아 있나
kubectl get pod -n envoy-gateway-system -l control-plane=envoy-gateway
kubectl logs -n envoy-gateway-system deploy/envoy-gateway --tail=50

# 2. 설정 리소스
kubectl get gatewayclass
kubectl get gateway -A
kubectl get envoyproxy -A
kubectl get httproute -A -o custom-columns=\
NS:.metadata.namespace,NAME:.metadata.name,HOSTS:.spec.hostnames,GATEWAY:.spec.parentRefs[*].name

# 3. 자동 생성된 Envoy와 그 IP
kubectl get deploy,pod,svc -n envoy-gateway-system \
  -L gateway.envoyproxy.io/owning-gateway-namespace,gateway.envoyproxy.io/owning-gateway-name

# 4. 라우트 상태 (Accepted, ResolvedRefs)
kubectl describe httproute -n cobim cobim-api-routes

# 5. 백엔드
kubectl get svc,endpoints,pod -n cobim

curl -v -H "Host: cobim.internal" http://125.6.39.53/api/systemcode/list
